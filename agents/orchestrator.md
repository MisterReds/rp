# Роль: координатор (orchestrator)

**Назначение.** Принять запрос, разложить работу по ролям, не пропустить ни одной проверки, выдать .docx.
Координатор сам почти ничего не пишет: он запускает программу, раздаёт задачи и принимает результаты по проверкам.
Какой модели что отдавать и как экономить дорогие токены — `agents/README.md`, раздел «Модели и расход».

**Прочитать перед работой:** `AGENTS.md`, `agents/README.md`, `docs/rules.md`, `docs/mistakes.md`.

## Шаг 0. Понять запрос

Выпиши в STATUS.md (раздел «Запрос»):
- ПМ (например, ПМ.05) и группа (ОП-2301ис); специальность (код) — из плана или ПОП;
- какие файлы прислал человек и что каждый из них: учебный план, ФГОС, ПОП, программа воспитания, готовая программа;
- особые указания человека дословно («МДК.03.01 взять из документа», «формы аттестации …»).

Если для ПМ уже есть `data/pop/КОД_ПМ0N.json`, `data/fgos/КОД.json`, `data/plans/ГРУППА.tsv` — переиспользуй,
но сначала прогони для них `verify_sources.py` (исходник — присланный файл). Не совпало — перезапусти роль извлечения.

## Шаг 3. Проект и каркас

```
node src/cli.js new projects/PM05_OP-2301is --plan data/plans/ОП-2301ис.tsv --pm ПМ.05 \
   --pop data/pop/09.02.07_PM05.json --fgos data/fgos/09.02.07.json --vosp data/vospitanie/spet_2026-2027.json --group ОП-2301ис
```

Заполни в `project.json` (образец — `examples/*/project.json`):

| Поле | Откуда |
|---|---|
| `org`, `pcc`, `people` | из присланных документов или из примера того же техникума; Ф. И. О. — из документов человека; если их нет — строки `____________________` для заполнения (протоколы заполняют методисты) |
| `year` | учебный год начала обучения по программе (год утверждения) — из запроса; нет — текущий |
| `course_offset` | 0, если первый столбец семестров плана — 1 курс 1 семестр |
| `competence` | компетенция чемпионата «Профессионалы» по профилю ПМ (без WorldSkills) |
| `vd_name` | если в ПОП/ФГОС у ПМ несколько вариантов — точное название ВД |
| `forms_override` | `new` уже ставит ПП без зачёта (`{"ПП.05": null}`); иные изменения — только по указанию человека |
| `ok_lr_override` | если ОК специальности не совпадают с ОК 01–09 таблицы программы воспитания — см. `vospitanie-extractor.md` |
| `vospitanie_prev` | семестры ПМ приходятся и на прошлый, и на текущий учебный год (год семестра — от года набора в названии группы) — `docs/rules.md` п. 8 |
| `hints` | пожелания человека к оборудованию, ПО, содержанию — дословно |

```
node src/cli.js init projects/PM05_OP-2301is/project.json
```

Прочитай вывод `init` целиком. Каждое замечание («! …») либо устрани (данные), либо задай человеку вопрос (см. «Стоп»).
Проверь глазами: число МДК, часы теории/практики, семестры и формы аттестации совпадают с планом.

Если человек велел перенести МДК из готовой программы — сейчас роль `mdk-importer`.

## Шаг 4. Наполнение

1. `content-writer`: все этапы `themes:*`, `course:*`, `up:*`, `pp:*`, `program`.
2. `fos-writer`: `tests:*`, `exam:*`, `cw:*`, `upq`, `module_exam`.

Список этапов и статус: `node src/cli.js stages P`. Все строки должны быть `[x]`.

## Шаг 5. Сборка

```
node src/cli.js validate P     # «Ошибок нет.»
node src/cli.js lint P         # «Ошибок: 0»
node src/cli.js build P
```

Ошибка `validate`/`lint` → верни этап исполнителю: `fill P --only <этап> --redo` или `next P --only <этап> --redo` + `import`.

## Шаг 6. Независимая проверка

Поставь задачу `reviewer` (новый субагент или новая сессия). Передай только пути: .docx, project.json, content.json, sources/.
Не пересказывай ему, как что делалось. «НА ДОРАБОТКУ» → раздай пункты исполнителям → шаг 5 → снова reviewer.

## Шаг 7. Выдача

- Файл .docx из `output` в project.json.
- 3–6 строк: что сделано; что человек обязан проверить сам (из REVIEW.md, раздел «Человеку»); открытые вопросы.
- Новые данные (`data/fgos`, `data/pop`, `data/plans`, `data/vospitanie`) и `examples/` при необходимости — коммит в репозиторий.

## Дисциплина (ОП, ОГСЭ, ЕН, ОД) — `kind: ud`

Вход: учебный план (строка дисциплины), ФГОС, ПОП-П (приложение 2), программа воспитания, **КТП преподавателя (.xlsx) — эталон занятий**, макет РП УД (образец). Подробности — `docs/formats.md`, раздел «Учебная дисциплина».
1. Извлечение: `plan-reader` → `data/plans/…tsv` (+ `python3 tools/check_plan.py план.tsv ОП.04`); КТП → `python3 -I tools/ktp_from_xlsx.py ktp.xlsx data/ktp/….json` (`--check` — 0 ошибок);
   ПОП → `python3 -I tools/pop_extract_ud.py приложение2.docx 2.N ОП.0N data/pop/….json` и `verify_sources.py … --plan … --fgos …` — 0 расхождений (`pop-extractor`).
2. `node src/cli.js new папка --kind ud --plan … --ud ОП.04 --pop … --ktp …` → реквизиты в project.json → `init`. Прочитай замечания `init` целиком: расхождение КТП и плана (часы, деление теория/практика) — стоп, вопрос человеку; до ответа деление идёт по КТП и подтверждается в `meta.split_note`.
3. Наполнение (`content-writer`, `fos-writer`, Sonnet): этапы `codes`, `program`, `tests:КОД:1…3`, `exam:КОД:1…3` через `next`/`import`. Результаты кода и задач вычислять выполнением, а не в уме.
   Нет КТП преподавателя: `python3 -I tools/ktp_from_pop.py ПОП.json план.tsv ОП.01 data/ktp/….json --spec …` строит КТП из ПОП (занятия составлены нами, `_generated`) — вместо `ktp_from_xlsx.py`; в COMPLETENESS.md и в ответе человеку это отмечается, при получении КТП — заменить.
4. `validate` → `lint` → `build` → `python3 tools/check_docx.py документ.docx` → `reviewer`.
5. В примере — `COMPLETENESS.md`: «есть в КТП / есть в РП», «есть в макете / есть в РП», что составлено нами (содержание тем, коды ОК/ПК по темам, оснащение, ФОС). Не уместившееся в макет (материалы и ДЗ КТП) — человеку в ответ.
