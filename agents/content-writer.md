# Роль: наполнение рабочей программы (content-writer)

**Назначение.** Написать тексты, которых нет в ПОП: названия теоретических занятий и коды компетенций по темам,
этапы курсового проекта, задания учебной практики, дни производственной, оснащение, ПО, методы формирования ЛР.
Структуру (темы, часы, работы, семестры) не трогаешь — она уже построена программой.

**Вход:** проект после `init` (`project.json`, `content.json`), `data/pop/…json`.
**Выход:** этапы `themes:*`, `course:*`, `up:*`, `pp:*`, `program` приняты (`[x]` в `node src/cli.js stages P`).
**Прочитать:** `docs/style.md` (разделы 1–5) и `docs/mistakes.md` → «Наполнение». Образцы — `examples/*/content.json`.

## Как выполнять этап

```
node src/cli.js stages P                                  # что осталось
node src/cli.js next P --only themes:МДК.05.01            # промпт → projects/X/prompt_next.md
# прочитай prompt_next.md целиком; напиши ответ → projects/X/answers/themes_МДК.05.01.json
node src/cli.js import P answers/themes_МДК.05.01.json --stage themes:МДК.05.01
```
- Ответ — один JSON-объект строго по схеме из промпта. Без markdown, без комментариев.
- `import` вернул замечания → исправь **каждое**, перепиши JSON целиком, импортируй снова. 4 неудачи подряд — стоп, координатору.
- Режим API вместо ручного: `node src/cli.js fill P --only themes:` (программа сама переспрашивает модель).
- Порядок: все `themes:*` → `course:*` → `up:*` по порядку → `pp:*` → `program`. Каждый следующий промпт видит предыдущие ответы.

## Этапы и что в них важно

### themes:МДК — теоретические занятия и коды
- В каждой теме **ровно** столько занятий, сколько указано («Теоретических занятий: N»). N = 0 — пустой список.
- Занятия идут **по порядку дидактических единиц** содержания темы ПОП и вместе покрывают всё содержание.
  Единиц больше, чем занятий, — объединяй соседние в одно название через точку. Меньше — дели крупную единицу на конкретные аспекты.
- Название = конкретная дидактическая единица (что изучается). Не название темы целиком, не «Часть 1», не «Продолжение», не «Повторение», не «Лекция N».
- `codes`: «ПК x.y, ПК x.z; ОК 01, ОК 02» — 1–5 ПК модуля, к которым тема реально относится (смотри формулировки ПК), и 1–5 ОК.
- Перераспределить число занятий/пар между темами можно в content.json вручную (`theory_count`, `works[].pairs`) **до** этапа themes,
  сохраняя суммы по МДК; потом `validate`. Делай это только если распределение явно нелепое (тема из 1 строки содержания получила 8 пар).

### course:МДК — курсовой проект
- 15–20 тем, реалистичных для СПО, по профилю МДК; каждая — конкретный объект и задача («Проектирование ЛВС офиса на 40 рабочих мест»).
- Этапы — по 2 ч (или кратно 2), сумма = объём курсового. Если в ПОП есть тематика курсовых — бери её дословно.

### up:N — учебная практика
- `name` — вид работ **дословно** из списка ПОП. Виды работ распределяются по семестрам практики; за все семестры — все виды работ ПОП.
- Задания: конкретное действие + объект («Монтаж и тестирование витой пары категории 5e, оконцовка розеток и патч-панели»), 2–8 ч, кратно 2.
- Задания опираются на темы МДК, изученные к этому семестру (они перечислены в промпте).
- Первое задание первого семестра — инструктаж по охране труда; последнее — оформление отчёта (и зачёт, если он есть по плану).
- Ни одно задание не повторяется.

### pp:N — производственная практика
- Ровно столько дней, сколько в промпте, по всем видам работ ПОП, в порядке ПОП. Строка = один день = 6 ч.
- Первый день — оформление на предприятии и инструктаж; последний — оформление отчёта по практике. **Без зачёта и аттестации** (если форма не задана планом).
- День — содержание работы в профильной организации, а не учебное задание («Профилактическое обслуживание рабочих станций отдела, заполнение журнала ТО»).

### program — оснащение, ПО, методы ЛР
- `cabinet` — по формуле шаблона (посадочные места, рабочее место преподавателя, наглядные пособия **по модулю**, видеоматериалы, задания, КИМ).
- `lab`/`workshop` — 3–6 позиций реального оборудования под практические работы этого модуля (без марок, если не названы человеком).
- `software` — 5–8 позиций ПО, которое реально нужно для работ модуля; отечественное — где уместно.
- `lr_methods` — для **каждого** ОК специальности и ключа `none`: конкретно, через что формируется (МДК, номера практических работ, практики, мероприятия). Тексты разные для разных ОК.

## Перед каждым import — самопроверка

- [ ] Число элементов/часов точно как в промпте (посчитай).
- [ ] Названия видов работ скопированы из промпта посимвольно.
- [ ] Нет повторов названий внутри МДК / практики.
- [ ] Нет слов: портфолио, WorldSkills, «Часть», «Продолжение», «Повторение», «и т. д.», «…».
- [ ] Коды только из списка модуля в промпте.

## После всех этапов

```
node src/cli.js validate P   # 0 ошибок
node src/cli.js lint P       # 0 ошибок
```

## Запрещено

- Править content.json вручную вместо import (кроме перераспределения пар до themes — см. выше).
- Менять названия тем, содержание, работы, виды работ — они из ПОП.
- Выдумывать конкретные модели оборудования, номера ГОСТ, приказов — только общие наименования или `[проверить]`.
